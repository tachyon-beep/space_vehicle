# Pathway to a complete vehicle

This is the capability plan, not a second copy of the model's numeric debt queue.
[Completion gates](docs/completion.md) define what green means;
[CONTRIBUTING.md](CONTRIBUTING.md) defines how a package lands. The vehicle is
currently in development with declared missing physical behavior. Current
counts are generated by the tools and checked against [README.md](README.md).

GitHub work-package issues are the source of delivery status, dependencies,
assignees, designs, child PRs and acceptance evidence. This document defines
scope and milestone order. Tool-derived debts/build-order remain the source of
field-level gaps. Do not equate closed issue counts or lines generated with
completion percentage. There is no credible completion date until evidence,
implementation size and runtime feasibility have been established.

## Risks and escalation

| Risk | Mitigation / decision point |
|---|---|
| Required physical evidence unavailable or inapplicable | WP02/WP03 bounded questions and effectivity checks; missing values stay unset; operator decides any scope/standard change |
| Local console checks conceal forked physical worlds | WP01 production-path two-window tracer before broad rule implementation |
| Strong configuration tests conceal absent physical behavior | WP11 executed coverage matrix plus independent references; strict lint alone cannot close V |
| Correct full model misses live or replay budget | WP12 correctness-first profiling; operator decides target changes, never silent clock dilation |
| Release/checkpoint or chassis mismatch invalidates trials | WP08 persistence contract and WP13 exact-SHA adoption/compatibility evidence |
| Independent reviewer or operator decision unavailable | Keep the issue blocked with the named approval/evidence need; do not invent a review or close the gate |

## First implementation batch after this scaffold

Start WP01's shared-executive design and bounded two-window tracer. Start WP02
and WP03 as bounded evidence questions, recording source applicability and dead
ends. Resolve WP08 clock/persistence policy before implementing it. Chassis
hardening is a separate programme in its own tracker and can run in parallel.
No physical fixes or campaign execution are part of publishing this scaffold.

Each broad capability is split into small child issues with observable acceptance
before code starts. A work package can accept incrementally implemented children
without claiming its final gate. If evidence or performance cannot meet scope,
raise a concrete operator decision with alternatives and consequences.

## Keep the programme honest

The implementer claims an issue and records a reviewer and design. A merged PR
links exact-SHA validation evidence. The reviewer checks the real path and
independent counterexamples; the maintainer closes only satisfied acceptance
criteria. At every milestone, review dependencies, blocked evidence, remaining
coverage, risks and the next ready batch. Keep unresolved decisions in
[decision records](docs/decisions/README.md). Changes to objective, evidence
standard or replay/live targets require operator approval.

A green development badge proves the development gate only. Strict readiness,
physical completeness, full mission acceptance, release, chassis adoption and
experiment acceptance are reported separately with their evidence links.
